# TXT-команды и личное окно — 19.10.2026

## Подтверждённые причины

1. **Удержание Alt.** Прежний личный ввод ждал отпускания модификаторов до показа окна и отменял попытку через 1,2 секунды. Если держать Alt в ожидании окна, пользователь не видел ничего. Теперь защищённое пассивное окно показывается сразу; перехват и подготовка игрового чата начинаются после отпускания клавиш. Сохраняются отмена по смене фокуса/профиля и общий таймаут.
2. **Редактор биндов.** `HandleBoundHotkey` запрещал Alt+T наравне с игровыми действиями. Приостановка TXT также отключала команду закрытия самого редактора. Теперь личный ввод доступен, а зарезервированные `!меню` / `!menu` остаются зарегистрированными. Ограничения остальных игровых действий сохранены.
3. **Английские команды.** Не было общего сопоставления английских имён и ввода в неверной раскладке. Новый `app/text_commands.ahk` строит одни маршруты для регистрации в чате и разбора личного ввода. Например: `!пдп` / `!pdp` / `!glg`, `!сву` / `!svu` / `!cde`, `!сигналы` / `!signals` / `!cbuyfks`.
4. **Неясное обозначение режима.** Старый режим «Окно AHK» намеренно отключает обычные команды в чате. Его видимое название заменено на **«Только окно AHK»**; второй режим называется **«Чат + окно AHK»**. Формат и значения старого INI совместимы, выбор пользователя не сбрасывается.

На чистом профиле исходная версия открывала Alt+T при обычном коротком нажатии. Поэтому нельзя утверждать, что отсутствие окна у пользователя всегда объясняется одним дефектом. Добавлена кнопка **«Восстановить Alt+T»** на странице TXT-команд: она восстанавливает поле клавиши и разрешает конфликт в настройках; затем нужно нажать **«Сохранить»**. Переключение через Alt+Esc на стенде не воспроизвелось и не объявляется установленной причиной.

## Совместимость и владение вводом

Явные TXT из настроек имеют приоритет над автоматически предлагаемыми именами. После повторной регистрации старые варианты раскладки снимаются; отключённая команда не получает английских алиасов. Для пользовательских сценариев добавляются варианты раскладки; английское смысловое имя им не выдумывается. Команды открытия: `!бинд`, `!bind`, `!,byl`, `!иштв`; эти варианты зарезервированы.

Личное окно подтверждает обычную команду пробелом или Enter; при редактировании текстов подтверждение остаётся на Enter. Оно не получает фокус. Подготовка уже открытого игрового чата выполняется владельцем ввода до запуска InputHook. `SafeSend` разрешает этому владельцу только `{Esc}` в фазе подготовки; текст, чужая операция, неправильное поколение или уже работающий hook исключение не получают. Отказ Windows в защите от захвата по-прежнему отменяет ввод с объяснением и не показывает приватный текст.

## Проверка

Протоколы лежат в `reports`: `text_bind_before_report.txt`, `text_bind_report.txt`, `private_input_report.txt`, `audit_selftest_report.txt`, `desktop_smoke_report.txt` и `summary.json`. Числа и контрольная сумма конечного EXE приведены в [общем отчёте](TEST_RESULTS_RU.md).

Стенд TXT использует полный граф приложения, настоящую загрузку профиля/INI, регистрацию hotkey/hotstring, Win32 Edit, события клавиш и InputHook. Для проверки удерживаемого Alt установлен наблюдатель клавиатуры. Статус игрового чата и ответ Capture API являются явными подменами: настоящая игра и кадры OBS не проверяются. Windows CI дополнительно пробует физическую Alt+T в RU/US, когда обе раскладки доступны; Wine явно пропускает эту группу.

Во время разработки обнаружена ошибка самого стенда: отметка видимости окна перезаписывалась после уничтожения HWND. Наблюдение теперь фиксируется до закрытия; отдельно проверяется освобождение состояния операции. Асинхронное открытие памятки проверяется после выполнения её таймера. Это исправления проверки, а не дополнительные заявленные дефекты приложения.

[Проверки в реальном клиенте](CLIENT_CHECKLIST_RU.md). Совместимость адресов клиента, фактическая отправка в Amazing, exclusive fullscreen и скрытие окон в записи OBS требуют проверки на пользовательском Windows.
