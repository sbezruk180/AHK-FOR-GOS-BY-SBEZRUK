# Проверка AHK FOR GOS — 22 октября 2026

Проверены обе формы приложения: EXE и обычный AHK, по три независимых прогона на настоящем Windows. Все семь специализированных стендов прошли во всех шести прогонах. Обнаружена воспроизводимая ошибка путей в диагностике обычного AHK и отсутствие необязательных изображений карт.

**Это не полная проверка каждой функции в Amazing.** Игрового клиента и OBS на стенде нет. Вход зафиксирован в 990 из 1383 функций приложения; оставшиеся функции и непроверенные игровые действия перечислены отдельно. Исходники приложения и распространяемый EXE в рамках аудита не изменены.

## Проверяемая версия и условия

- Исходники приложения соответствуют релизу `806ee76aa6d31a65e4b74f03fd79cc6bf6539af2`. Соответствие всех исходников встроенному манифесту EXE проверено по SHA-256.
- `release/AHK_FOR_GOS.exe`: 5 308 928 байт, SHA-256 `5c43313efdbf5b960dbce5198ef9c30f56881cdaa3c6a383ffcddc33501083c5`.
- Нативный Windows runner, AutoHotkey 1.1.37.02 **ANSI x86**: `A_IsUnicode=0`, `A_PtrSize=4`, `GetACP=1251`. Не замена на Unicode x64/Wine.
- Английский Windows runner требует локализации ANSI. Поэтому полные сценарии EXE выполнялись на временной копии релиза с добавленным `activeCodePage=ru-RU` в PE-манифест. Изменён только ресурс типа 24; остальные ресурсы и секции программы побайтово проверены. Обычный AHK запускался официальным ANSI x86 runtime с тем же локальным манифестом и `/CP1251`.
- Отдельно проверен запуск неизменённого распространяемого EXE. Полный прогон именно неизменённых байтов EXE на Windows с русской системной локалью не выполнялся. Хеши исходных и временных host-файлов сохранены в [probe](reports/deep-20261022/native-locale-probe/probe.json) и сводках.
- Пользовательские конфигурации не использовались: отдельные рабочие каталоги и INI, созданные настоящим запуском приложения. Для исходников добавлена отдельная проверка переносимого режима с данными рядом с кодом.
- Неинструментированное приложение и отдельная копия со счётчиками проверялись раздельно. Счётчики добавлены после деклараций функции; рабочие исходники не затрагивались.

## Подтверждённые проблемы

### 1. Диагностика обычного AHK путает каталог данных с каталогом программы

Места: `app/diagnostics.ahk:422–429`, `445–449`, `812–827`.

`RunSelfTestV1()` и `RunDiagnosticsExport()` ищут `helper.ahk`, `UDF.ahk`, `common.ahk` и файлы laws относительно `AppHost_DataDir()`. При запуске исходника с отдельным `--data-dir` эти файлы существуют рядом с основным скриптом, но диагностика ищет их в папке настроек.

Результат в каждом из трёх неинструментированных AHK-прогонов: selftest — 24 Critical и 47 High, diagnostics — 5 ошибок. Среди них ложные сообщения об отсутствии обработчика цели и кэша Auto ID: текст UDF не прочитан из правильного места. **Это не 76 отдельных поломок и не доказательство неисправного Auto ID.**

Воспроизведение после обычного первого запуска с инициализированным INI:

```text
AutoHotkeyA32.exe /CP1251 AHK_FOR_GOS_BY_SBEZRUK.ahk --selftest --data-dir C:\AHKGOS-TestData
AutoHotkeyA32.exe /CP1251 AHK_FOR_GOS_BY_SBEZRUK.ahk --diagnostics --data-dir C:\AHKGOS-TestData
```

Контроль: те же исходники и runtime с данными рядом со скриптом прошли selftest и diagnostics трижды. Скомпилированная версия проходит эти проверки с отдельной папкой данных, поскольку читает встроенные ресурсы. Исправление при следующей работе: разделить пути исходников/ресурсов и изменяемых данных, сохранив INI и отчёты в каталоге данных. В рамках этого аудита изменение приложения не внесено.

### 2. Отсутствуют 17 необязательных изображений карт

Selftest и diagnostics сообщают предупреждение для 11 групп карт. Официальные ссылки и группы валидны, но локальные картинки не поставляются. Это недостаток комплектации, а не найденная ошибка поиска законодательства. Протокол с путями сохранён в `original_diagnostics_report.txt`.

### Что не подтвердилось как ошибка приложения

- В полной матрице есть сырые `FAIL` запуска второго экземпляра: первый вариант стенда не нажимал OK в ожидаемом предупреждении. Дублирующий GUI не появлялся. Исправлена только обработка окна в тестовом Python-коде; повторный нативный прогон всех шести запусков — PASS, все предупреждения подтверждены, выход штатный.
- Два `FAIL` в GUI-тесте обычного AHK относятся к требованиям EXE. В сырых данных они сохранены; адаптер помечает их `EXPECTED_EXE_ONLY_ASSERTIONS`.
- Предшествующие ошибки TXT-стенда были вызваны неверным именем тестового процесса в скомпилированном fixture. В итоговом прогоне используется имя реально запущенного host; приложение не менялось.

Полный повтор запускается вручную через Actions → **Repeated EXE and source audit**. Локально на Windows:

```text
python tools/deep_audit.py --probe --output C:\Audit\probe
python tools/deep_audit.py --form exe --repeat 1 --output C:\Audit\deep-exe-1
python tools/deep_audit.py --form source --repeat 1 --output C:\Audit\deep-source-1
python tools/startup_audit.py --output C:\Audit\startup
```

Для полной матрицы повторить обе формы с `--repeat 2` и `3`. Проверки не должны выполняться одновременно на одном рабочем столе: им нужен фокус клавиатуры. Сводку и карту собирает `tools/summarize_deep_audit.py`; наличие шести завершённых записей и соответствие исходников релизному EXE проверяются автоматически. Сам факт завершения CI не заменяет чтение содержащихся в отчёте ошибок.
